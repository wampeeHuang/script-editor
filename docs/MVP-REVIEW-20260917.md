# 从 Descript 调研到本地文案工作台 MVP

日期：2026-09-17。性质：整改建议，非已确认 PRD，不授权实施或发布。

## 结论

最快且可信的首发：一个面向中文解说、知识短视频创作者的本地文案到旁白工作台。

用户导入或撰写文案，按声音分组录音/采用音频，试听和局部返工，自动保存，得到可在外部剪辑工具使用的文案与旁白。工程统一保存在本应用项目文件夹内，可重开、恢复和按 ID 定位。

不把它定位为本地 Descript，也不把“修改文字能剪辑现有媒体”作为首发承诺。最小应削减能力宽度，而不是削减保存、恢复、状态表达和交付质量。

## 1. Descript 应借鉴什么，不借鉴什么

| 调研启发 | 本项目的翻译 | 不照搬的部分 |
|---|---|---|
| 三个视图共享同一份工程数据 | 文案、声音状态、试听和导出来自同一工程与采用记录 | 不直接推出词级媒体剪辑 |
| 项目容器与编辑域分开 | 项目库管理工程；编辑器只显示当前稿件的工具 | 不引入所有者、共享、租户/工作区 |
| 原件与编辑副本分工 | 原录音保留，采用音频单独登记，缓存可重建 | 短音频首发无需云上传与视频代理管线 |
| 按状态开放功能 | 无录音不能导出声音，过期声音需要重录；就地说明原因 | 不堆满置灰的未来功能 |
| 所有渠道共享导入状态 | 文本导入和已有工程接入复用选择/校验组件 | 原工程打开与新建文本工程仍是两种语义 |
| 非破坏性与失败恢复 | 文案撤销、原录音保留、回收站、历史恢复可验证 | 不急于实现删除词/忽略词/多轨序列 |

重要纠偏：Descript 纠正转录文字并不改变底层音视频；它的媒体剪辑依赖词时间映射。文稿是重要操作表面，但不是足以表达所有媒体属性的唯一数据对象。本产品必须区分“改计划中的台词”与“修正录音的转写”。首发只支持前者：改稿后原声音保留，但标记为不再匹配当前文案，需要重新录制/生成。

## 2. 当前最需要整改的断点

### P0：工程可以保存，却未必可以可靠找回

前端 recentScripts() 从 localStorage 读列表，项目路由也用该列表寻找 ID。磁盘工程存在不等于列表存在；清理浏览器数据或换浏览器后，入口可能失联。需要服务端本地工程登记与默认 projects 根的索引重建。

同时 Workspace.load_project() 遇到缺失 project.json 会返回 new_project()；该模板含一个章节。openRecentScript() 只检查 segments.length，无法据此区分旧工程已打开还是加载到新模板。必须分离“读取已存在工程”和“创建空白工程”；缺失、损坏和格式不兼容不得回退为成功。

### P0：保存与恢复的质量门禁不够明确

service.py 的保存仍是直接 write_text 覆盖 project.json，没有同目录临时文件加原子替换；读写竞争和中断窗口需要修复。前端 refresh() 无请求版本检查，旧响应回填可能覆盖更晚的编辑状态；doSave() 成功后直接 clearDraft()，也需要只清除对应已确认版本，不能把保存途中产生的新草稿一并清掉。这些是代码识别的风险，本轮没有构造损坏真实工程去复现。

另一个明确代码问题：/api/history/restore 在请求 Handler 内调用 self._keep_history()，但该方法定义在 Workspace 上。建议先修正并在隔离工程验证“恢复一版、再恢复回来”，不能仅因为有历史目录就宣称可恢复。

### P0：试听与交付不是同一条时间线

audioTimeline() 仅拼接有效采用单元，不加入旧导出模型的段间间隙；exporter 仍提供六件套及遗留投放。当前不足以承诺“在这里听到的就是导出的”。工程音频覆盖不完整时，还可能给人已经完成整篇旁白的误解。

首发需要统一采用声音清单、间隙规则、播放顺序、真实时长与导出音轨。估时与实际声音时间必须分开。无真实句内时戳时，不默认导出看起来精确的逐句 SRT。

### P1：入口重复且全局外壳混合不同能力域

“打开”和“最近项目”重复；搜索文案声称搜索项目/稿件/素材，但实际只是项目名称筛选；编辑器沿用首页全局导航，导致当前稿件工具与库级管理混杂。需要收口信息架构，而不是再加主页卡片或更多顶栏按钮。

### P1：项目身份稳定，句子身份仍是位置编号

normalize_project() 与 orderedProject() 会重新编号 i，补丁也按 i 找句子。插入/重排后，外部工具持有的旧句号可能指向别句。因此“通过 ID 给其他项目调取脚本”需先交付项目级只读快照；句级回写在稳定 sentenceId 与 revision 出现后再开放。

### P1：文档存在相互覆盖的历史说法

HANDOFF、PRD、RECORDING-STAGE 用不断追加覆盖的方式记录变化，存在旧布局、旧后端、精确字幕承诺与新范围并置。建议建立一份简短首发合同，其余历史记录保留但明确不作为当前承诺。

## 3. 最小但完整的首发范围

首发限定：Windows 本地、单用户、一个工程一份稿件、中文解说/口播文案、一个声音轨。

主路径：项目库 → 新建/导入文案 → 写改 → 免费朗读打磨 → 录音或采用外部音频 → 试听/局部返工 → 导出。

必须保留：

1. 本地项目库：名称、真实/预估时长、创建时间、最近打开、搜索、排序、日期筛选、回收站。
2. 文案编辑：章节、句行、粘贴拆分、撤销重做、MD/TXT 导入预览。
3. 声音制作：当前声音分组录音，试听后采用；音频导入明确绑定范围，不把整篇长录音自动切成词/句。
4. 状态：未录、已采用、文案已改、处理失败、保存失败。颜色之外有文字说明。
5. 保存恢复：磁盘自动保存、异常草稿恢复、历史恢复、清空浏览器数据后仍能找到磁盘工程。
6. 简单交付：干净 TXT/MD；完整有效旁白 WAV；不完整时仅显式导出选中分组并声明范围，不悄悄跳过缺失内容。

已有豆包配音作为可选增强：保留当前接线和显式成本确认，但不让首发依赖凭证、额度与声音质量。先复用已有录音路径，不为“AI 产品”标签临时增加新模型。

暂缓：视频/PPT/图层编排、词级剪辑、ASR/强制对齐、自动剪口头禅、多轨多人、多合成、多文件并行、语音克隆、内置模型切换、云协作、分享发布、Agent 自动回写。旧下游六件套保留兼容，但不作为首发默认入口。工程压缩包可作为后续迁移能力，不阻塞本机单用户内测。

## 4. UI 收口建议

项目库侧栏：新建、项目、导入、回收站，设置在底部。打开与最近列表合并；“添加已有工程…”放在项目页，作为找回/接入入口。默认根内工程自动登记，外部旧工程明确登记位置，不在评审时自动搬迁用户文件。

编辑器：顶部返回项目、当前名称、保存状态及单一导出动作；中间文稿；右侧仅展示当前所选声音分组的录音/配音面板；底部单一播放控制，更多轨道细节按需展开。不会重复把项目库动作和全文生产按钮塞满编辑页。

保留已接近 Descript 的低密度列表、统一内容左边线、整行悬停色块、16px 画布外间距与当前导航留白。整体统一 Vivi 色板及输入焦点细框规则，不再在多个候选 Logo/颜色方案之间反复横跳。Logo 定稿是一项视觉验收，不应成为闭环阻塞。

画布眉页只显示真实可行动提示：保存失败、可恢复草稿、素材缺失。正常时隐藏或很克制，不能用营销条填空白。搜索范围如只搜项目就写“搜索项目”，不承诺尚无索引的素材搜索。

## 5. 技术路线：小步改造，不重写

保留 Python 服务、model.py 分组与内容哈希缓存、FFmpeg 音频处理、当前工程目录及设计 tokens。不为了学习 Descript 更换 React/Redux、引入协同框架、构建 GPU 调度或桌面壳。

最小补充：

- project.json：schemaVersion、projectId、revision；磁盘文件作为已提交版本真相源，前端为当前编辑状态，index.json 是派生缓存。
- 本地目录索引：ID → 项目基目录；服务端保存，可从默认 projects 根重新扫描。最近打开等库级元数据不再只有浏览器一份。第一版不需要同时上 SQLite 与 JSON；小规模先一个可重建的 JSON 索引，规模证据出现后再升级。
- 保存：项目级串行写、revision 校验、同目录原子替换、对应版本备份；前端旧响应不回填新版本。
- 声音资产：采用记录明确声音分组、文本版本/哈希、相对路径、真实时长和来源。原录音是资产，不应被当成可删除缓存。外部导入的采用资产复制到工程管理范围。
- 统一声音清单：试听、WAV 导出和时长读取同一组有效资产与间隙。
- 只读项目快照：按 projectId 返回 schemaVersion/revision/文案/采用资产摘要，不开放无版本校验的句号回写。

前端已有 3164 行及多轮 CSS 覆盖。只在修改触及处抽取库页、导入和工程状态职责，冻结当前视觉基线；不把全面拆模块当作上线前置任务。安全和一致性修复先于代码整洁。

## 6. 最快发布顺序与门禁

| 批次 | 改动 | 通过标准 |
|---|---|---|
| A 工程可信 | 库索引、严格打开、原子保存、版本检查、历史恢复 | 隔离工程清空浏览器存储仍可找回；无效路径/损坏 JSON 明确失败；延迟响应不覆盖新稿；恢复再恢复可逆 |
| B 声音闭环 | 有效资产覆盖、统一声音清单、实际 WAV 导出 | 修改一组只使对应声音失效；其他组保留；导出与试听顺序/间隙一致；总时长误差不超过最终输出一个采样点，不靠“看起来同步”验收 |
| C 产品收口 | 合并重复入口、统一主题、缩窄默认工具、文本导出 | 从项目库完成新建/导入/重开/录音/导出；无占位主动作，无横向覆盖；1280px 与900px主路径可操作 |
| D 小范围内测 | 一键启动、依赖预检、3份真实文案、用户反馈 | 麦克风拒绝/服务中断有恢复出口；独立启动重开真实工程；真实用户无需口头指导完成旁白交付 |

建议先发本机可用内测，再给少量目标创作者试用。上述门禁是待实施目标，不是已通过结果。不承诺固定几天；声音导出一致性、保存恢复及真实麦克风测试是关键耗时项。公网上线/正式发布属于另一轮授权。

小范围验证建议：3—5名目标创作者，每人至少完成一份真实文案；观察完成率、无助完成、返工次数、找回工程、导出后外部剪辑使用。目标不是证明市场已经成立，而是判断这个细分闭环是否比他们现有的文本编辑器+录音文件夹更省事。

## 7. 什么情况下才值得扩大范围

用户能稳定把中文稿件变成可交付旁白，并且频繁卡在同一个后续环节时再扩张。如果卡在文本与录音精确对应，考虑对齐；如果卡在录音回改，考虑替换/裁剪；如果卡在配画面，先做明确的下游交付协议，未必在本应用里再做视频编辑器。

首发核心承诺：写完能听、改完知道哪段要重做、离开不丢、回来能找到、导出与听到的一致。
