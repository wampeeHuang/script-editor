## 0. 定位：一刀切在整条链路的哪一段

用户完整链路：

```
选题调研 → 脚本撰写 → 脚本修改/审核 → 配音录制 → 字幕/时间戳 → 画面匹配 → 剪辑合成 → 发布
```

**本次交付：中间四段（脚本撰写 → 脚本修改/审核 → 配音录制 → 字幕/时间戳）合并为一个交互循环。**

- 上游「选题调研」：不做，产出物（要点列表）直接以多行文本粘进来即可。
- 下游「画面匹配」：**只做字段与预览**（段挂镜头指令 + 画面叠加到真机预览），不做可视化编排。
- 「剪辑合成」「发布」：不做。但导出物必须**直接喂给现有 `build.sh`**，把该脚本里手写的段:镜头数换成受 manifest 驱动。

## 1. 第一性原理：问题在「作用单位」错位，不在工具少

链路里每一环其实都是**同一份数据的投影**，但各自用了不同的刻度尺：

| 环节 | 当前作用单位 | 实证 |
|---|---|---|
| 写 | 句（换行即分句） | 现有 v2 模型 |
| TTS | 段（整段一次合成） | `tts/batch.jsonl` 每行一个整段 narration |
| 时间戳 | **估算的句**（按字数切） | `build/subs.srt` 时间由字数比例推出，非 TTS 返回 |
| 画面 | 镜头（挂段下，数量手写） | `build.sh` 里 `declare -A SEGS=( [1]=1 [2]=2 … )` |
| 构建 | 手写常量 | 同上 + 字幕参数硬编码在内联 python |

刻度不统一，只能靠**人工搬运**对齐，于是产生三类损耗：

1. **时间损耗**：改一句 = 导出 → 整段重合成 → 重算切分 → 重建 → 十几分钟。
2. **精度损耗**：句级时间戳是估算的，字幕与声音不对齐；误差沿句子累积。
3. **一致性损耗**：改脚本要人肉同步 `SEGS`、字幕参数、batch.jsonl 三处。

### 结论：统一作用单位为「句」，所有投影自动派生

推导出两个**自动成立**的结论：

- **时间戳不再需要"打点"。** TTS 以句为单位合成时，句边界本身就是时间戳。v2 PRD 里「边听边按 Enter」那套劳动在 TTS 路线下直接消失；仅在自录路线降级为兜底（本次不做）。
- **"改脚本"和"听效果"可以合并成同一个动作。** 这不是省几步点击，而是行为层面的改变：反馈延迟从 15 分钟压到 1 秒，人才可能真的逐句打磨；否则只会一遍过。**这是本需求的核心价值，也是所有设计取舍的最高优先级。**

## 2. 方案一句话

> 把「段 → 句」两层列表做成唯一真值；改一句只重算该句所在段，时间轴纯数学重排；
> 听觉反馈由流式 TTS 在 0.5 秒内给出，精确时间戳由后台通道补齐；
> 人和 agent 提交同一种结构化补丁，所以「改了哪几句」是机器可判定的。

### 核心不变量（不变量优先于功能）

| # | 不变量 | 为什么 |
|---|---|---|
| I1 | `句` 是唯一时间刻度。任何时间值都是派生量，不允许手工写死 | 消除估算与人工同步 |
| I2 | **合成单位 = 句末标点界的「整句」**（实测选定，§4.1）；未改动的单元永不重复合成；付费合成只在显式批量时发生 | 合成是唯一有成本、有延迟的操作；单元粒度兼顾连贯性与增量成本 |
| I3 | 人和 agent 走同一条写路径（补丁），无第二条 | 保证状态单一来源，agent 可安全介入 |
| I4 | **文本 → 能听到的最短路径必须免费且即时**（本机朗读 < 0.5s）；付费合成永远是显式动作 | 既让"逐句打磨"这个行为可能发生，又不烧钱。二者解耦是这条可变的关键 |
| I5 | 重放已生成的音频 = 0 成本 | 成本只发生在"文本变了"这一刻，纠正手感时可放心反复听 |
| I6 | 导出的旧合同文件（script.json / SRT / md 表 / batch.jsonl）保持向后兼容 | 不打断既有成片管线 |

## 3. 数据模型：真值 vs 派生

**真值（唯一写入口，必须落盘）**

```jsonc
{
  "meta": {
    "title": "掼蛋指南",
    "canvas": { "w": 1920, "h": 1080, "fps": 30 },
    "gapBetweenSegments": 0.45,          // 段间静音，来自 build.sh 常量
    "backends": [                        // 成本策略是后端属性，不是全局开关（§4.2）
      { "id": "browser", "label": "本机朗读",  "cost": "free", "auto": true,  "keep": false },
      { "id": "indextts", "label": "IndexTTS25·克隆", "cost": "free", "auto": true },
      { "id": "doubao",  "label": "豆包·小何",  "cost": "paid", "auto": false,
        "pricePer1kChars": 0,            // 由用户填，工具不猜
        "resourceId": "seed-tts-2.0", "speaker": "zh_female_xiaohe_uranus_bigtts" }
    ],
    "subtitle": { "orr": "p", "font": "Noto Serif SC", "size": 4.2,
                  "bottom": 8, "stroke": true, "bar": false,
                  "fontSource": "字荐/localhost:8770" }
  },
  "segments": [
    { "id": "s1", "title": "开场·小红书",
      "backend": "indextts",                              // 可按段指定音色/后端
      "shots": [ { "kind": "scroll", "scrollToText": "从这里开始",
                   "annotations": [{ "findText": "从这里开始", "shape": "ellipse" }] } ] }
  ],
  "sentences": [
    { "i": 1, "sid": "s1", "text": "姐妹们，人齐了，我们来掼蛋！" }
  ]                                       // ↑ 时间、单元切分、音频全部不在真值里
}
```

**派生缓存**：`narration/index.json`（可再生，可删除，绝不手改）

```jsonc
{
  "units": [
    { "uid": "s1u1", "sid": "s1", "text": "姐妹们，人齐了，我们来掼蛋！",
      "sentenceIds": [1],
      "audio": "narration/units/s1u1.wav", "hash": "…",
      "status": "clean",                  // clean | dirty | synthesizing | failed
      "backend": "indextts", "chars": 14, "duration": 2.78 }
  ],
  "sentences": [ { "i": 1, "start": 0.225, "end": 2.555 } ]
}
```

> 真值（`project.json`）与派生缓存（`index.json`）分离：前者人可读可 diff 可进 git，后者随时可重建。**改文案只动真值，缓存随之失效** —— 这是"编辑永不触发合成"（§4.2）的落点。

**关于 `audio` 的位置**：音频挂在**段**上（合成单位 = 段，§4.1）；句只存文本，时间全部派生。

**派生（自动计算，不许手工写）**

| 派生量 | 来源 |
|---|---|
| **`unit` 切分** | 段内按**句末标点**（`。！？`）把句分组；无标点时整段为 1 个单元（§4.1） |
| `unit.audio` | 对该单元文本整段合成（一单元一文件） |
| `sentence.t.start / end` | 两层时间轴：骨架 = 单元边界（构造而来，0 误差）+ 细分 = 单元内逗号行按字符权重（§4.4） |
| `segment.duration` | Σ 该段各单元音频时长 + 段内单元间 gap |
| 任一句的全局时间 | 段起始偏移（Σ 前段时长 + gap）+ 段内偏移 |
| `subs.srt` | 句级 `t` |
| `文案脚本.md` | 句级 `t` + 段归属 |
| `build/manifest.json` | 段→镜头数、段时长、画布、字幕参数 |
| `script.json` | 段的 `narration` = 该段所有句按序拼接 |
| `tts/batch.jsonl` | 每单元一行 `{"text": unit_text}` |

> 三层职责澄清：
> - **段** = 叙事 + 画面单元（挂镜头）；也是缓存与音色的最小单位
> - **合成单元（unit）** = 音频单元 —— 按句末标点切出的「整句」，**合成单位**，决定连贯性与增量粒度
> - **句** = 时间 + 字幕单元 —— 你的"一行"，按逗号断，是细化层
>
> 镜头挂在段下，时长 = 段总时长 ÷ 镜头数（与现有 `build.sh` 语义一致，但不再手写）。

## 4. 六个关键机制

### 4.1 合成单位：句末标点界的「整句」（实测选定）

**可量化的问题**：逐句合成会不会让子句以「说完了」的降调收尾？—— 能测。用行尾 F0 斜率（半音/秒，负值 = 下坠）。

**实验**（`_runtime/ab_synth2.py`：同一文本 / 同一音色 / 同一后端，四种方案）：

| 方案 | 合成单元 | 调用 | **逗号结尾行的行尾斜率** | 行响度离散度 |
|---|---|---|---|---|
| A 整段 | 全段 1 个 | 1 | **+2.37**（上扬·承接） | 0.79 dB |
| B 逗号行逐句 | 每行 1 个 | 5 | **−5.47**（下坠·说完） | 1.26 dB |
| C 逗号行逐句·无尾标点 | 每行 1 个 | 5 | 数据不可靠（见结论三） | 0.88 dB |
| **D 句末标点分组** | 按 `。！？` 切 | **3** | **+1.84** | **0.62 dB** |

**结论一（假设成立）**：B 与 A 在**同一批点位上符号相反**，差约 7.8 半音/秒。逐句合成确实把承接语气改成了收束语气。

**结论二（比预期更好）**：**D 几乎等于 A**（+1.84 vs +2.37），响度一致性还最好（0.62 dB）。因为每个合成单元都以真正的句末标点收尾，单元内部的逗号处语调完全正常。

→ **选定 D：合成单位 = 句末标点界的「整句」（可含多个逗号行）。**

比 A 更好：增量粒度更细（改一个逗号行只需重合成它所在的整句），且与 §4.4 两层时间轴**天然对齐** —— 单元边界 = 骨架（构造而来，0 误差），单元内的逗号行 = 细分。

**结论三（"没有标点符号"）**：C 的 5 次调用里有 2 次行尾斜率出现 **−45.74 / −39.27 半音/秒** 的野生值 —— 正常语音不可能出现，是基频追踪失败。**去掉行尾标点后，TTS 的语调输出变得不可预测**（它失去了判断语气的依据），而不是稳定变差。**不可预测比稳定变差更糟，因为无法补偿。**

→ 由此定下**无标点时的退化规则**：若文本没有任何句末标点，**退化为"整段作为一个合成单元"**（即方案 A，不切分）。这样单元结尾永远是文本结尾，不会出现"半句话被单独合成"。

**两个我主动作废的指标**（不用错误数字误导决策）：

- **行接口静音**：`librosa.effects.split` 会把短停顿并入有声区间，B 测出 0.029s 明显失真，不可用。
- **总时长**：四种方案 11.76~12.98s，**无实质差异**。此前说"逐句会长 20%"是测量口径造成的假象，此处更正。

> **最终判定权在你耳朵**：`_runtime/ab-synth/` 已生成等响度归一的 `A.wav / B.wav / C.wav / D.wav`，以及顺序对比 `compare_sequence.wav`（A→B→D→C，段间 0.8s）。数字用于定位差异在**哪个点位、哪个方向**；听感用于确认差异**是否真的刺耳**。

### 4.2 成本模型：花钱只发生在"文本变了"这一刻

**第一性事实**：重放已生成的音频 = **0 成本**（读本地文件）。**只有"文本变了、需要新声音"才产生费用。** 所以成本控制 = 控制合成的 **时机 / 范围 / 后端** 三个变量。

**关键设计：成本策略是后端的属性，不是全局开关。**

| 后端 | 成本 | 允许自动重合成 |
|---|---|---|
| 本机朗读（浏览器 `speechSynthesis`） | **0**，不留档 | ✅ |
| IndexTTS25（可克隆音色） | **0**（本地） | ✅ |
| CosyVoice3 / Confucius4-TTS | **0**（本地） | ✅ |
| 豆包（云端） | **按字符计费** | ❌ 必须显式触发 |

→ "**除非它很便宜**"自动成立：用免费后端时改完即自动重合成；切到豆包才需要手动。

**三级触发**

| 级 | 触发 | 合成范围 | 成本 | 用途 |
|---|---|---|---|---|
| **L0 朗读** | 光标停在句上 / 点 `🔊` | 该句 | **0** | 判断拗口、长度、同音歧义 —— 任何声音都听得出来，不需要真音色 |
| **L1 试听** | 点 `⟳` | **单段**（当前后端） | 免费后端 0；豆包按该段字符计费，按钮上先显字数 | 听真音色在这一段的效果 |
| **L2 定稿** | 点「更新配音」（显式） | **所有脏单元**（去重） | 确认窗显示：N 单元 / M 字 / 预估费用 / 预计耗时 | 整片质量与时间轴刷新 |

**L0 是保住 I4 的关键**：即时反馈由免费本机朗读承担，付费合成永远是显式动作。两者解耦，所以"逐句打磨"这个行为仍然可能发生，且不烧钱。

**省钱核心 = 攒批 + 去重**

- 编辑期间**永不触发合成**，只标脏
- 连改 10 处 → 点一次「更新配音」→ 只合成这 10 处**去重后**的段
- 未改段命中缓存，一个字都不重合成（I2）

> **这正是"一次调整完确认调整之后再更新"，把它做成产品机制。**

> **单价不写死**：工具里是后端配置项 `price_per_1k_chars`（本地后端填 0）。预估金额永远按你填的口径算，不依赖任何猜测的数字。

### 4.3 音频格式：中间态无损，边界处转换

格式真正起作用只有三个场合：① 导出给下游/播放器的兼容性；② 需要无损的中间处理（拼接、VAD 分析、多轮重编码）；③ 体积与传输速度。**内部用什么本身无所谓**，关键是别让同一个文件反复编解码。

| 角色 | 格式 | 理由 |
|---|---|---|
| L1 试听（`preview.mp3`） | `.mp3` 24kHz | 小、快、用完即弃，追求快速出声 |
| L2 定稿（`master/seg-%04d.wav`） | `.wav` 24kHz 无损 | 后续要过对齐分析、与镜头拼接、可能多轮处理；避免有损代际损失 |
| 导出 | 按下游需求转 | ffmpeg 读 wav 无障碍；需要 mp3 时在导出这一步转一次 |

**规则：全程最多一次有损编码，且发生在最终交付那一步。** 两者兼有不是妥协，是正确做法。

### 4.4 时间戳：两层时间轴（骨架精确 + 细分有界）

**问题重述**：合成单位必须是「段」（§4.1），所以时间戳只能事后对齐。而事后对齐的两条路，实测都不够：

| 候选 | 实测结果 | 结论 |
|---|---|---|
| VAD 找**行**边界 | 豆包逗号处不停顿（2.94s→7.39s 连续），−35/−40/−45/−50dB 四档全漏检 | ❌ **无解**（音频里没这条边界） |
| 本地 faster-whisper large-v3 字级 | **平均误差 239ms / 最大 488ms**，系统性偏早约 400ms；还把"掼蛋"听成"灌蛋"（匹配率 0.847） | ❌ 不够用 |

**解法：拆成两层，各层只用自己能可靠获得的粒度。**

```
骨架层（合成单元边界 = 句末标点）  ← 构造而来，0 误差，零成本
   └── 细分层（用户的逗号行）      ← 骨架区间内按字符权重细分，误差有界、不累积
```

| 层 | 单位 | 来源 | 精度 |
|---|---|---|---|
| **骨架** | 合成单元边界（= `。！？`） | **构造而来** —— 逐单元合成，边界直接由音频时长前缀和得出。**0 误差、零成本、不依赖任何后端、不需要 VAD、不需要强制对齐** | 精确 |
| **细分** | 用户的逗号行 | 骨架区间内按字符权重切 | ±150~250ms，**封顶在单元内** |

> **§4.1 选定「句末标点分组」后，对齐工具链全部消失。** 骨架边界是合成时构造出来的，不是事后猜出来的 —— 所以不需要 VAD、不需要豆包时间戳、不需要 WhisperX（原 D5 这个问题就此消解）。事后对齐只在一种情况下才需要：**自录音**（音频连续，无法按单元构造边界），那属于实验性能力。

**为什么这比现状好一个量级**：掼蛋管线现在是**全局按字数估算**，误差沿整片累积（100s 处可能偏好几秒）；两层方案把误差**封顶在单个合成单元内**，永不跨单元累积。

**附带好处**：不需要为时间戳改变断行习惯（继续按逗号断，保字幕可读性）。

> **「事后推断」路线已被实测否定**（记录备查，`_runtime/align-test/`）：
> - VAD 找**行**边界：豆包逗号处不停顿（2.94s→7.39s 连续），−35/−40/−45/−50dB 四档全漏检，漏检处崩到 1515ms
> - faster-whisper large-v3 字级：平均 239ms / 最大 488ms，系统性偏早约 400ms，还把"掼蛋"听成"灌蛋"
>
> 这两条记录是选择「构造边界」而不是「推断边界」的直接依据。`align.py` 保留了 `align_by_vad`（含"候选不足即失败"硬校验）与 `align_by_words`（LCS），供自录音等特殊场景使用。

### 4.5 单元级增量重算

- 缓存键 = `hash(单元文本) + hash(后端与音色参数)`。单元内任一字符变化 → 该单元键失效 → **只重合成该单元**。
- 边界效应要处理：改一处可能改变单元的**切分**（例如把句中的 `，` 改成 `。` 会拆出一个新单元）。所以脏单元按「文本哈希比对」判定，而非按下标 —— 切分变化时只影响相邻单元。
- 时间偏移 = Σ(前面所有单元时长 + 段间/单元间 gap)。**纯数学，O(n)，零合成。**
- 未改单元的音频文件直接复用，一次调用都不重复（I2）。
- 脏单元在新音频产出前，时间轴沿用**上一次的时长**并标记为 `stale`（不是断裂），所以定稿前时间轴依然可用、可预览。

### 4.6 补丁协议（人机同权，I3）

人和 agent 都提交同一种结构化补丁，工具只认补丁：

```jsonc
{
  "patchId": "p-0007",
  "intent": "这句太书面了，改口语",       // 人给的指令，或 agent 自述
  "ops": [
    { "op": "replaceText",     "i": 7,   "text": "就挂我小红书上，点开就能看。" },
    { "op": "insertAfter",     "i": 8,   "sid": "s3", "texts": ["…", "…"] },
    { "op": "delete",          "ids": [9] },
    { "op": "setSegmentTitle", "sid": "s3", "title": "认级牌+逢人配" },
    { "op": "setShots",        "sid": "s3", "shots": [ … ] }
  ],
  "reasoning": "……"                      // 可选，展示给人看
}
```

补丁应用后，工具自动得出「哪些句变了」→ 推导「哪些段脏了」→ 只重合成脏段。**这是增量重算能成立的前提，也是 agent 敢介入而不炸掉整条时间轴的原因。**

三条入口（同一份 ops 格式）：
- 人在工具里直接打字改 → 工具内部生成补丁
- 人在工具内**指令框**写"这句太书面，改口语" → 进指令队列 → agent 读队列 → 回写补丁
- agent 主动发起（如"整段压缩到 3 句"）→ 直接 POST 补丁

## 5. 交互循环（改稿、听声、定稿三段分离）

**核心机制：编辑与合成完全解耦。编辑永远免费，合成永远显式。**

```
① 打磨期（连续改，零成本）
   改字 / 下指令 → 只标脏 ──────────────► 不触发任何合成
   │
   ├─ 光标停在句上 (L0) → 本机朗读 0.3s 出声 ◄── 0 成本、零延迟  「听顺不顺」
   │
   └─ 点 ⟳ (L1) → 合成该段 ─────────────► 免费后端=0；付费后端先显字数

② 确认期
   用户说「这批改完了」→ 点「更新配音」
   └─ 弹窗：将合成 N 段 / M 字 / 预估费用 / 预计耗时 → 确认

③ 定稿期（批量，可后台）
   逐单元合成（单元 = 句末标点界的整句，保连贯）
   ├→ 音频落盘 narration/units/s1u2.wav（一单元一文件）
   ├→ 两层时间轴：骨架（单元边界，构造而来 0 误差）+ 细分（逗号行按字符权重）
   ├→ 偏移重排（Σ 前面单元时长 + gap，纯数学）
   └→ SRT / md 表 / manifest 全部自动刷新
```

**这样安排解决了三件事同时成立**：

| 要求 | 由谁满足 |
|---|---|
| 精细调整要**语音连贯** | 合成单位 = 句末标点界的整句（§4.1，实测选定） |
| 改一处就要**马上听** | L0 本机朗读，免费即时（I4） |
| 不能**自动烧钱** | 付费合成只在 ② 显式确认后发生；免费后端才允许自动（§4.2） |

**合起来一句话：打磨时零成本零等待，花钱只在你确认要花钱的那一刻。**

## 6. UI 结构：三分保留，把"搬运"删掉

### 6.0 先纠正一个抽象错误

上一版把三视图定义成「改数据 / 看数据 / 送数据」（按**读写权限**切）。这是选错了维度，症状很明显：必须给"看数据"硬塞体检信号、给"送数据"硬塞健康检查才能把这两格填满。**需要硬凑才能填满，就说明抽象错了。**

正确的切分维度是**产物 × 焦点** —— 而这恰好回到原方案的「写脚本 / 录音配音 / 生成时间戳」三分。三份产物天然对应三种不同的注意力：

| 侧栏格 | 视图 | 产物 | 焦点 | 节奏 |
|---|---|---|---|---|
| 1 | **稿** | 文本 | 结构、文案、画面字段 | 低频创造 |
| 2 | **声** | 音频 | 音色、语速、合成状态、A/B | 低频决策 |
| 3 | **轴** | 时间 | 全片时间轴、字幕、体检 | 低频核对 |

**「交付」不是视图，是动作。** 它不产出新东西，只是个出口 → 降级为顶部工具栏的「导出」「投放」两个按钮。

> 修正说明：I3「唯一写路径」是**机制层**不变量（人和 agent 都提交同一种补丁），不是"只有一个视图能改"。上一版把它误读成 UI 层的"唯一写入口"，才逼得「稿」吞下所有编辑功能。

### 6.1 关键论证：独立 ≠ 解耦

"三个视图交叉在一起会不会太复杂"——担心合理，但结论反了：

- **旧世界（三个独立工具）= 独立但耦合。** 物理上分开，逻辑上必须靠**人工搬运**串起来：写脚本 → 导出 md → 配音工具载入 md → 合成 → 打点 → 导出 LRC。每个工具都不得不自备一整套「打开 / 保存 / 另存 / 导入 / 导出」，因为数据不会自己流动。**这才是真正的交叉。**
- **新世界 = 耦合但独立。** 逻辑上一体（改文案，音频与时间自动跟着变），视图之间**零接口**（不需要任何搬运控件）。

一句话：**把耦合从人身上挪到代码里。** 人只看到三个干净的视图，"搬家"由真值层做掉。所以统一真值之后视图不是变重，而是**可以变薄** —— 省掉的正是每个视图里那套重复的导入导出。

### 6.2 高频循环不跨页（"改↔听"降维成行内控件）

真正的矛盾只有一个：**高频循环（改一下→听一下）要求同屏，产物审阅要求分区。**

解法：**循环降维，视图只承载低频决策。**

```
每句行内： [ 文案输入框 ] [🔊 朗读] [▶ 成品] [⟳ 试听] [⚠ 脏] [2.4s]
                          ↑0 成本   ↑0 成本  ↑当前后端·可能计费
```

改字（行内）→ `🔊` 出声（行内）→ 标脏（行内）→ **不自动合成** → 时长更新（批量定稿后）。**整个循环在一行内闭合，任何视图都不需要为它让路，且打磨期零成本。**

同理：**真机字幕预览不是「轴」独占，而是可停靠面板**（默认常驻右侧，延续 v2 光标行实时渲染；在「轴」视图里放大成全片）；**指令框**选中即现；**脏标记**在所有视图可见。

### 6.3 各视图内容

**① 稿（可离线独立使用）**

- 段/句结构：增删段、增删句、改字、改段标题、调段序
- 画面字段：段挂镜头指令（`scrollToText` / `annotations` / 图片或视频路径），预览以叠加层呈现
- 行内控件：`🔊` 本机朗读（0 成本）/ `▶` 播放成品音频（0 成本）/ `⟳` 试听（当前后端，付费则显字数）/ `⚠` 脏 / 时长 / 字数
- 指令框：选中句或段 → 写自然语言 → 进队列 → agent 回补丁
- **不需要服务即可用**（只写文本与画面字段），满足 A9 降级要求

**② 声**

- **三级触发控制台**（§4.2）：L0 本机朗读开关（默认开）、L1 试听后端、**L2「更新配音」主按钮**
- **成本仪表**：当前后端成本属性、本次将合成多少字、预估费用（单价来自配置，不写死）；付费后端旁常显"计费"标记
- 后端清单：音色 / 语速 / 情感，**可按段指定**（不同段不同音色）
- 合成队列：哪些段脏了、排队中、失败可重试、已完成；每段显示 `chars / duration / backend`
- 批量动作：全量重合成、只重合成脏段（默认）、同段 A/B 试听不同音色
- 试听历史：回切对比上一版
- 后端健康：各后端可用性、密钥来源（只显示"已从环境变量读取"，不显示值）

**③ 轴**

- 句级时间条：每句一段横条，长度 ∝ 时长，颜色区分 clean / dirty
- 段分隔 + 段间 gap 可视化；顶部全局 mm:ss 标尺
- **体检信号**：`end ≤ next.start` 自洽性、段偏移、**字数÷时长异常句高亮**（如"8 个字占 5 秒"→ 合成可能出错或文本有误），点击跳回「稿」对应句
- 目标时长：设定目标（如小红书 60s），显示"超出 12s，建议删减 N 句"——**只给建议，不给拖动**
- **本次改动影响预览**：受影响句数、总时长变化 Δ（见 6.4）
- **时间不可手调**：要改时间只有两个正当入口 —— 改脚本，或调语速/后端。这是 §1 的推论，不是偷懒

### 6.4 一个真实风险与对策

数据自动派生有个副作用：用户可能**"看不见"派生发生了什么** —— 改了文案，音频和时间在后台悄悄变了。这是「耦合」的真实代价，必须显式补偿：

- 脏标记常显，不自动隐藏
- 「轴」视图给出改动影响预览（受影响句数 + 总时长 Δ）
- 批量重合成前提示将影响的段数

> 附：字体沿用系统字体 + 字荐（localhost:8770）清单；**导出只记字体名 + 来源**，不嵌字体。

## 7. 技术形态

从「纯静态」升级为「单页 + 极小本地服务」：

**工程目录：私有工作目录 + 显式投放**（推荐，待确认）

工具运行中会频繁改 master、产生临时文件，若直接写进成片管线的 `tts/`，半成品会混进生产目录。所以工作区与投放区分离：

```
<视频项目>\                              例如 D:\workspace\2026-09-14-掼蛋指南视频\
├── _runtime\
│   ├── narration\                       ← 工具私有工作目录（新增，不动既有三个）
│   │   ├── project.json                 真值
│   │   ├── preview.mp3                  临时试听，不留档
│   │   ├── units\s1u1.wav               成品音频（一单元一文件）
│   │   ├── exports\                     五件套草稿
│   │   └── backup\<时间戳>\             投放前的自动备份
│   ├── script\script.json               ← 投放时写入（既有位置）
│   ├── tts\seg-0001.wav                 ← 投放时写入（既有位置）
│   └── build\subs.srt · 文案脚本.md      ← 投放时写入（既有位置）
└── 掼蛋指南-小红书版.mp4
```

理由：① 不污染既有三目录；② **投放是显式动作**（延续 v2「投放到录音 →」心智），点一下才进生产目录；③ 产物与成片同处一地，`build.sh` 相对路径不用改；④ 投放时若目标文件已存在，先自动备份到 `backup\<时间戳>\` 再覆盖（注意 `seg-0001.wav` 这个文件名是合同要求的，与 IndexTTS 产物同名是预期的 —— 你在重做旁白）。

尚未归属视频项目的草稿（新选题、试写）落 `D:\tools\script-editor\projects\<slug>\`，之后"另存为项目"再迁入视频目录。打开项目用 `showDirectoryPicker()` + IndexedDB 记住目录句柄，实现"最近项目"。

## 10. 验收标准

| # | 标准 | 判据 |
|---|---|---|
| A1 | 免费即时反馈 | 点 `🔊` 到出声 < 0.5s（本机朗读）；**改文案不触发任何付费合成**（断言付费调用计数 = 0） |
| A2 | 单元级增量 + 攒批 | 连改 5 处文案 → 断言合成调用 = **0**（只标脏）；点「更新配音」后 = 受影响的**单元数**次；未改单元调用 = 0 |
| A3 | 时间戳误差有界 | 骨架层误差 0；行边界（细分层）与真值偏差 ≤ 250ms，且**不跨句累积**（第 N 行误差不随 N 增长） |
| A4 | 时间轴自洽 | 句序单调且 `end ≤ next.start`（允许停顿间隙，间隙归语音之间的静音）；段偏移 = Σ 前段时长 + gap；Σ句时长 + Σ段内间隙 ≈ 段总时长 |
| A5 | 旧合同可消费 | 导出的 `script.json` / `batch.jsonl` / `文案脚本.md` 直接喂现有 `build.sh` 成功出片 |
| A6 | 人机同权 | agent 补丁与人在 UI 的同等操作，产生的 project.json 完全一致 |
| A7 | 后端不泄露密钥 | 全仓库 grep 无 key 明文；只读环境变量 |
| A8 | 前端门禁 | Vivi 令牌溯源（`var` 直引 `tokens/vivi-tokens.css`）、无默认样式、无 CDN、控制台零报错 |
| A9 | 降级可用 | 服务未启动时前端可用（编辑/保存/预览/导出），仅 TTS 相关按钮提示离线 |
| A10 | 成本可见 | 付费后端每次合成**前**显示将消耗的字符数；定稿前显示 N 段 / M 字 / 预估费用 / 预计耗时（单价取自后端配置项，不写死） |

**验证方式**：Chrome DevTools MCP `evaluate_script` 做功能断言（不用 vision 数像素），`take_screenshot` 做渲染检查（沿用 HANDOFF 已确定的规范）。

**风险**
